## React Compiler {/*react-compiler*/}

React Compiler больше не является исследовательским проектом: компилятор теперь используется на сайте instagram.com в продакшене, и мы работаем над выпуском компилятора на дополнительных платформах в Meta и подготовкой первого выпуска с открытым исходным кодом.

Как обсуждалось в нашем [предыдущем посте](/blog/2023/03/22/react-labs-what-we-have-been-working-on-march-2023#react-optimizing-compiler), React *иногда* может выполнять слишком много перерендеров при изменении состояния. С первых дней React нашим решением для таких случаев была ручная мемоизация. В наших текущих API это означает применение API [`useMemo`](/reference/react/useMemo), [`useCallback`](/reference/react/useCallback) и [`memo`](/reference/react/memo) для ручной настройки количества перерендеров React при изменении состояния. Но ручная мемоизация — это компромисс. Она загромождает наш код, легко допускает ошибки и требует дополнительных усилий для поддержания актуальности.

Ручная мемоизация — разумный компромисс, но мы не были удовлетворены. Наше видение заключается в том, чтобы React *автоматически* перерендеривал только нужные части пользовательского интерфейса при изменении состояния, *не ставя под угрозу основную ментальную модель React*. Мы считаем, что подход React — пользовательский интерфейс как простая функция от состояния со стандартными значениями и идиомами JavaScript — является ключевой частью того, почему React был понятен для столь многих разработчиков. Вот почему мы инвестировали в создание оптимизирующего компилятора для React.

JavaScript — это язык, который, как известно, сложно оптимизировать, благодаря его нестрогим правилам и динамической природе. React Compiler может безопасно компилировать код, моделируя как правила JavaScript, *так и* «правила React». Например, компоненты React должны быть идемпотентными — возвращать одно и то же значение при одних и тех же входных данных — и не могут изменять пропсы или значения состояния. Эти правила ограничивают возможности разработчиков и помогают создать безопасное пространство для оптимизации компилятора.

Конечно, мы понимаем, что разработчики иногда немного нарушают правила, и наша цель — сделать так, чтобы React Compiler работал из коробки с как можно большим количеством кода. Компилятор пытается обнаружить, когда код строго не соответствует правилам React, и либо компилирует код, если это безопасно, либо пропускает компиляцию, если это небезопасно. Мы тестируем на большой и разнообразной кодовой базе Meta, чтобы помочь подтвердить этот подход.

Разработчикам, которым интересно убедиться, что их код соответствует правилам React, мы рекомендуем [включить строгий режим](/reference/react/StrictMode) и [настроить плагин ESLint для React](/learn/editor-setup#linting). Эти инструменты могут помочь выявить тонкие ошибки в вашем коде React, улучшая качество ваших приложений сегодня и делая ваши приложения более перспективными для будущих функций, таких как React Compiler. Мы также работаем над консолидированной документацией по правилам React и обновлениями нашего плагина ESLint, чтобы помочь командам понять и применить эти правила для создания более надежных приложений.

Чтобы увидеть компилятор в действии, вы можете посмотреть наш [доклад с прошлой осени](https://www.youtube.com/watch?v=qOQClO3g8-Y). Во время доклада у нас были ранние экспериментальные данные о попытке использования React Compiler на одной странице instagram.com. С тех пор мы внедрили компилятор в продакшене на сайте instagram.com. Мы также расширили нашу команду, чтобы ускорить развертывание на дополнительных платформах в Meta и для открытия исходного кода. Мы рады предстоящему пути и поделимся дополнительной информацией в ближайшие месяцы.

## Actions {/*actions*/}

Мы [ранее сообщали](/blog/2023/03/22/react-labs-what-we-have-been-working-on-march-2023#react-server-components), что изучаем решения для отправки данных с клиента на сервер с помощью Server Actions, чтобы вы могли выполнять мутации в базе данных и реализовывать формы. Во время разработки Server Actions мы расширили эти API для поддержки обработки данных и в клиентских приложениях.

Мы называем эту более широкую коллекцию функций просто «Actions». Actions позволяют передавать функцию элементам DOM, таким как [`<form/>`](/reference/react-dom/components/form):

```js
<form action={search}>
  <input name="query" />
  <button type="submit">Search</button>
</form>
```

Функция `action` может работать синхронно или асинхронно. Вы можете определить их на стороне клиента, используя стандартный JavaScript, или на сервере с помощью директивы [`'use server'`](/reference/rsc/use-server). При использовании action React будет управлять жизненным циклом отправки данных за вас, предоставляя хуки, такие как [`useFormStatus`](/reference/react-dom/hooks/useFormStatus) и [`useActionState`](/reference/react/useActionState), для доступа к текущему состоянию и ответу действия формы.

По умолчанию Actions отправляются в рамках [перехода](/reference/react/useTransition), сохраняя интерактивность текущей страницы во время обработки action. Поскольку Actions поддерживают асинхронные функции, мы также добавили возможность использовать `async/await` в переходах. Это позволяет вам отображать ожидающий пользовательский интерфейс с состоянием `isPending` перехода при запуске асинхронного запроса, такого как `fetch`, и отображать ожидающий пользовательский интерфейс на протяжении всего применения обновления.

Наряду с Actions мы представляем функцию под названием [`useOptimistic`](/reference/react/useOptimistic) для управления оптимистичными обновлениями состояния. С помощью этого хука вы можете применять временные обновления, которые автоматически отменяются после фиксации окончательного состояния. Для Actions это позволяет вам оптимистично установить окончательное состояние данных на клиенте, предполагая, что отправка прошла успешно, и вернуться к значению для данных, полученных с сервера. Он работает с использованием обычного `async`/`await`, поэтому он работает одинаково, независимо от того, используете ли вы `fetch` на клиенте или Server Action с сервера.

Авторы библиотек могут реализовать пользовательские пропсы `action={fn}` в своих собственных компонентах с помощью `useTransition`. Наше намерение состоит в том, чтобы библиотеки приняли шаблон Actions при разработке своих API компонентов, чтобы обеспечить согласованный опыт для разработчиков React. Например, если ваша библиотека предоставляет компонент `<Calendar onSelect={eventHandler}>`, рассмотрите возможность предоставления API `<Calendar selectAction={action}>` тоже.

Хотя изначально мы сосредоточились на Server Actions для передачи данных между клиентом и сервером, наша философия для React заключается в предоставлении одной и той же модели программирования на всех платформах и в любых средах. По возможности, если мы представляем функцию на клиенте, мы стремимся сделать так, чтобы она также работала на сервере, и наоборот. Эта философия позволяет нам создать единый набор API, которые работают независимо от того, где работает ваше приложение, что упрощает обновление до различных сред в будущем.

Actions теперь доступны в канале Canary и будут выпущены в следующем релизе React.

## Новые функции в React Canary {/*new-features-in-react-canary*/}

Мы представили [React Canaries](/blog/2023/05/03/react-canaries) в качестве опции для принятия отдельных новых стабильных функций, как только их дизайн будет близок к завершению, до того, как они будут выпущены в стабильной версии semver.

Canaries — это изменение способа разработки React. Ранее функции исследовались и разрабатывались в частном порядке внутри Meta, поэтому пользователи видели бы только окончательный отполированный продукт при выпуске в Stable. С помощью Canaries мы разрабатываем публично с помощью сообщества, чтобы доработать функции, которыми мы делимся в серии блогов React Labs. Это означает, что вы узнаете о новых функциях раньше, когда они дорабатываются, а не после их завершения.

React Server Components, Asset Loading, Document Metadata и Actions уже появились в React Canary, и мы добавили документацию по этим функциям на react.dev:

- **Директивы**: [`"use client"`](/reference/rsc/use-client) и [`"use server"`](/reference/rsc/use-server) — это функции бандлера, разработанные для полностековых фреймворков React. Они отмечают «точки разделения» между двумя средами: `"use client"` инструктирует бандлер сгенерировать тег `<script>` (как [Astro Islands](https://docs.astro.build/en/concepts/islands/#creating-an-island)), в то время как `"use server"` сообщает бандлеру сгенерировать конечную точку POST (как [tRPC Mutations](https://trpc.io/docs/concepts)). Вместе они позволяют вам писать многоразовые компоненты, которые объединяют интерактивность на стороне клиента с соответствующей логикой на стороне сервера.

- **Document Metadata**: мы добавили встроенную поддержку для рендеринга тегов [`<title>`](/reference/react-dom/components/title), [`<meta>`](/reference/react-dom/components/meta) и метаданных [`<link>`](/reference/react-dom/components/link) в любом месте вашего дерева компонентов. Они работают одинаково во всех средах, включая полностью клиентский код, SSR и RSC. Это обеспечивает встроенную поддержку функций, разработанных такими библиотеками, как [React Helmet](https://github.com/nfl/react-helmet).

- **Asset Loading**: мы интегрировали Suspense с жизненным циклом загрузки ресурсов, таких как таблицы стилей, шрифты и скрипты, чтобы React учитывал их при определении того, готовы ли отображаться содержимое в таких элементах, как [`<style>`](/reference/react-dom/components/style), [`<link>`](/reference/react-dom/components/link) и [`<script>`](/reference/react-dom/components/script). Мы также добавили новые [API загрузки ресурсов](/reference/react-dom#resource-preloading-apis), такие как `preload` и `preinit`, чтобы обеспечить больший контроль над тем, когда ресурс должен загружаться и инициализироваться.

- **Actions**: Как было сказано выше, мы добавили Actions для управления отправкой данных с клиента на сервер. Вы можете добавить `action` к таким элементам, как [`<form/>`](/reference/react-dom/components/form), получить доступ к статусу с помощью [`useFormStatus`](/reference/react-dom/hooks/useFormStatus), обработать результат с помощью [`useActionState`](/reference/react/useActionState) и оптимистично обновить пользовательский интерфейс с помощью [`useOptimistic`](/reference/react/useOptimistic).

Поскольку все эти функции работают вместе, их сложно выпускать по отдельности в канале Stable. Выпуск Actions без дополнительных хуков для доступа к состояниям формы ограничит практическую применимость Actions. Внедрение React Server Components без интеграции Server Actions усложнит изменение данных на сервере.

Прежде чем мы сможем выпустить набор функций в канал Stable, нам нужно убедиться, что они работают согласованно и у разработчиков есть все необходимое для их использования в продакшене. React Canaries позволяют нам разрабатывать эти функции по отдельности и постепенно выпускать стабильные API до тех пор, пока весь набор функций не будет завершен.

Текущий набор функций в React Canary завершен и готов к выпуску.

## Следующая основная версия React {/*the-next-major-version-of-react*/}

После нескольких лет итераций `react@canary` теперь готов к выпуску в `react@latest`. Новые функции, упомянутые выше, совместимы с любой средой, в которой работает ваше приложение, предоставляя все необходимое для использования в продакшене. Поскольку Asset Loading и Document Metadata могут быть критическим изменением для некоторых приложений, следующая версия React будет основной версией: **React 19**.

Предстоит еще многое сделать для подготовки к выпуску. В React 19 мы также добавляем давно запрашиваемые улучшения, которые требуют критических изменений, таких как поддержка Web Components. Сейчас мы сосредоточены на том, чтобы внести эти изменения, подготовиться к выпуску, доработать документацию по новым функциям и опубликовать объявления о том, что включено.

Мы поделимся дополнительной информацией о том, что включает в себя React 19, как принять новые клиентские функции и как создать поддержку React Server Components в ближайшие месяцы.

## Offscreen (переименовано в Activity). {/*offscreen-renamed-to-activity*/}

С момента нашего последнего обновления мы переименовали возможность, которую мы исследуем, из «Offscreen» в «Activity». Название «Offscreen» подразумевало, что оно применимо только к частям приложения, которые не были видны, но при исследовании этой функции мы поняли, что части приложения могут быть видимыми и неактивными, например, контент за модальным окном. Новое название более точно отражает поведение пометки определенных частей приложения как «активных» или «неактивных».

Activity все еще находится в стадии исследования, и наша оставшаяся работа заключается в доработке примитивов, которые предоставляются разработчикам библиотек. Мы снизили приоритет этой области, пока мы сосредоточены на выпуске более завершенных функций.
