## Что такое конкурентный React? {/*what-is-concurrent-react*/}

Самое важное дополнение в React 18 — это то, о чем, как мы надеемся, вам никогда не придется думать: конкурентность. Мы думаем, что это в основном верно для разработчиков приложений, хотя для сопровождающих библиотек ситуация может быть немного сложнее.

Конкурентность, как таковая, не является функцией. Это новый механизм, происходящий за кулисами, который позволяет React одновременно подготавливать несколько версий вашего пользовательского интерфейса. Вы можете думать о конкурентности как о детали реализации — она ценна из-за функций, которые она открывает. React использует сложные методы в своей внутренней реализации, такие как очереди приоритетов и множественная буферизация. Но вы не увидите эти концепции ни в одном из наших общедоступных API.

При разработке API мы стараемся скрыть детали реализации от разработчиков. Как разработчик React, вы сосредотачиваетесь на *том*, как должен выглядеть пользовательский опыт, а React обрабатывает *как* предоставить этот опыт. Поэтому мы не ожидаем, что разработчики React будут знать, как работает конкурентность под капотом.

Однако конкурентный React важнее, чем типичная деталь реализации — это фундаментальное обновление основной модели рендеринга React. Поэтому, хотя не очень важно знать, как работает конкурентность, возможно, стоит знать, что это такое на высоком уровне.

Ключевым свойством конкурентного React является то, что рендеринг прерываемый. Когда вы впервые обновитесь до React 18, прежде чем добавлять какие-либо конкурентные функции, обновления будут отображаться так же, как и в предыдущих версиях React — в одной, непрерывной, синхронной транзакции. При синхронном рендеринге, как только обновление начинает рендериться, ничто не может прервать его, пока пользователь не увидит результат на экране.

В конкурентном рендере это не всегда так. React может начать рендеринг обновления, сделать паузу посередине, а затем продолжить позже. Он может даже полностью отказаться от выполняемого рендера. React гарантирует, что пользовательский интерфейс будет выглядеть согласованно, даже если рендеринг прерван. Для этого он ждет выполнения изменений DOM до конца, после того как будет оценено все дерево. С этой возможностью React может подготавливать новые экраны в фоновом режиме, не блокируя основной поток. Это означает, что пользовательский интерфейс может немедленно реагировать на ввод данных пользователем, даже если он находится в середине большой задачи рендеринга, создавая плавный пользовательский опыт.

Другим примером является повторно используемое состояние. Конкурентный React может удалять разделы пользовательского интерфейса с экрана, а затем добавлять их обратно позже, повторно используя предыдущее состояние. Например, когда пользователь переходит на другой экран и возвращается, React должен иметь возможность восстановить предыдущий экран в том же состоянии, в котором он был раньше. В предстоящем минорном выпуске мы планируем добавить новый компонент под названием `<Offscreen>`, который реализует этот шаблон. Аналогичным образом, вы сможете использовать Offscreen для подготовки нового пользовательского интерфейса в фоновом режиме, чтобы он был готов до того, как пользователь его откроет.

Конкурентный рендеринг — это мощный новый инструмент в React, и большинство наших новых функций созданы для того, чтобы воспользоваться им, включая Suspense, переходы и потоковую отрисовку на стороне сервера. Но React 18 — это только начало того, что мы намерены построить на этой новой основе.

## Постепенное внедрение конкурентных функций {/*gradually-adopting-concurrent-features*/}

Технически, конкурентный рендеринг — это критическое изменение. Поскольку конкурентный рендеринг прерываем, компоненты ведут себя немного по-другому, когда он включен.

В ходе нашего тестирования мы обновили тысячи компонентов до React 18. Мы обнаружили, что почти все существующие компоненты «просто работают» с конкурентным рендерингом, без каких-либо изменений. Однако некоторые из них могут потребовать дополнительных усилий по миграции. Хотя изменения обычно небольшие, у вас все равно будет возможность вносить их в своем собственном темпе. Новое поведение рендеринга в React 18 **включается только в тех частях вашего приложения, которые используют новые функции.**

Общая стратегия обновления состоит в том, чтобы запустить ваше приложение на React 18, не нарушая существующий код. Затем вы можете постепенно начать добавлять конкурентные функции в своем собственном темпе. Вы можете использовать [`<StrictMode>`](/reference/react/StrictMode), чтобы помочь выявить ошибки, связанные с конкурентностью, во время разработки. Strict Mode не влияет на поведение в продакшене, но во время разработки он будет регистрировать дополнительные предупреждения и дважды вызывать функции, которые должны быть идемпотентными. Он не поймает все, но он эффективен для предотвращения наиболее распространенных типов ошибок.

После обновления до React 18 вы сможете сразу же начать использовать конкурентные функции. Например, вы можете использовать startTransition для навигации между экранами, не блокируя ввод данных пользователем. Или используйте useDeferredValue для регулирования ресурсоемких повторных рендеров.

Однако в долгосрочной перспективе мы ожидаем, что основным способом добавления конкурентности в ваше приложение будет использование библиотеки или фреймворка с поддержкой конкурентности. В большинстве случаев вы не будете напрямую взаимодействовать с конкурентными API. Например, вместо того, чтобы разработчики вызывали startTransition при переходе на новый экран, библиотеки маршрутизации будут автоматически оборачивать навигацию в startTransition.

Может потребоваться некоторое время, чтобы библиотеки обновились до конкурентной совместимости. Мы предоставили новые API, чтобы упростить библиотекам использование конкурентных функций. Тем временем, пожалуйста, наберитесь терпения к сопровождающим, пока мы работаем над постепенной миграцией экосистемы React.

Для получения дополнительной информации см. нашу предыдущую публикацию: [Как обновиться до React 18](/blog/2022/03/08/react-18-upgrade-guide).

## Suspense в фреймворках данных {/*suspense-in-data-frameworks*/}

В React 18 вы можете начать использовать [Suspense](/reference/react/Suspense) для получения данных в предвзятых фреймворках, таких как Relay, Next.js, Hydrogen или Remix. Специальное получение данных с помощью Suspense технически возможно, но по-прежнему не рекомендуется в качестве общей стратегии.

В будущем мы можем предоставить дополнительные примитивы, которые могут упростить доступ к вашим данным с помощью Suspense, возможно, без использования предвзятого фреймворка. Однако Suspense работает лучше всего, когда он глубоко интегрирован в архитектуру вашего приложения: ваш маршрутизатор, ваш уровень данных и ваша среда рендеринга на стороне сервера. Поэтому даже в долгосрочной перспективе мы ожидаем, что библиотеки и фреймворки будут играть решающую роль в экосистеме React.

Как и в предыдущих версиях React, вы также можете использовать Suspense для разделения кода на клиенте с помощью React.lazy. Но наше видение Suspense всегда было связано с гораздо большим, чем просто загрузка кода — цель состоит в том, чтобы расширить поддержку Suspense, чтобы в конечном итоге один и тот же декларативный запасной вариант Suspense мог обрабатывать любую асинхронную операцию (загрузку кода, данных, изображений и т. д.).

## Server Components все еще находится в разработке {/*server-components-is-still-in-development*/}

[**Server Components**](/blog/2020/12/21/data-fetching-with-react-server-components) — это предстоящая функция, которая позволяет разработчикам создавать приложения, охватывающие сервер и клиент, сочетая богатую интерактивность приложений на стороне клиента с улучшенной производительностью традиционной отрисовки на стороне сервера. Server Components не связаны по своей природе с Concurrent React, но они разработаны для наилучшей работы с конкурентными функциями, такими как Suspense и потоковая отрисовка на стороне сервера.

## Что нового в React 18 {/*whats-new-in-react-18*/}

### Новая функция: автоматическая группировка обновлений {/*new-feature-automatic-batching*/}

Группировка — это когда React группирует несколько обновлений состояния в один повторный рендер для повышения производительности. Без автоматической группировки мы группировали обновления только внутри обработчиков событий React. Обновления внутри промисов, `setTimeout`, нативных обработчиков событий или любых других событий по умолчанию не группировались в React. С автоматической группировкой эти обновления будут группироваться автоматически:

```js
// До: группировались только события React.
setTimeout(() => {
  setCount(c => c + 1);
  setFlag(f => !f);
  // React выполнит рендеринг дважды, по одному разу для каждого обновления состояния (без группировки)
}, 1000);

// После: обновления внутри таймаутов, промисов,
// нативных обработчиков событий или любых других событий группируются.
setTimeout(() => {
  setCount(c => c + 1);
  setFlag(f => !f);
  // React выполнит рендеринг только один раз в конце (это и есть группировка!)
}, 1000);
```

Для получения дополнительной информации см. эту статью [Автоматическая группировка для меньшего количества рендеров в React 18](https://github.com/reactwg/react-18/discussions/21).

### Новая функция: переходы {/*new-feature-transitions*/}

Переход — это новая концепция в React для различения срочных и несрочных обновлений.

*   **Срочные обновления** отражают прямое взаимодействие, такое как ввод текста, нажатие кнопки и т. д.
*   **Обновления перехода** переводят пользовательский интерфейс из одного представления в другое.

Срочные обновления, такие как ввод текста, нажатие кнопки или клавиши, требуют немедленного отклика, чтобы соответствовать нашей интуиции о том, как ведут себя физические объекты. В противном случае они кажутся «неправильными». Однако переходы отличаются тем, что пользователь не ожидает увидеть каждое промежуточное значение на экране.

Например, когда вы выбираете фильтр в раскрывающемся списке, вы ожидаете, что сама кнопка фильтра отреагирует немедленно при нажатии. Однако фактические результаты могут переходить отдельно. Небольшая задержка будет незаметной и часто ожидаемой. И если вы измените фильтр снова до того, как результаты будут отрендерены, вам нужно будет увидеть только последние результаты.

Как правило, для наилучшего пользовательского опыта одно пользовательское действие должно приводить как к срочному, так и к несрочному обновлению. Вы можете использовать API `startTransition` внутри события ввода, чтобы сообщить React, какие обновления являются срочными, а какие — «переходами»:

```js
import { startTransition } from 'react';

// Срочно: показать введенный текст
setInputValue(input);

// Пометить любые обновления состояния внутри как переходы
startTransition(() => {
  // Переход: показать результаты
  setSearchQuery(input);
});
```

Обновления, обернутые в `startTransition`, обрабатываются как несрочные и будут прерваны, если поступят более срочные обновления, такие как нажатия кнопок или клавиш. Если переход прерывается пользователем (например, путем ввода нескольких символов подряд), React отбросит устаревшую работу по рендерингу, которая не была завершена, и отрендерит только последнее обновление.

*   `useTransition`: хук для запуска переходов, включая значение для отслеживания состояния ожидания.
*   `startTransition`: метод для запуска переходов, когда хук не может быть использован.

Переходы будут использовать конкурентный рендеринг, который позволяет прерывать обновление. Если контент приостанавливается повторно, переходы также сообщают React, чтобы он продолжал показывать текущий контент, выполняя рендеринг контента перехода в фоновом режиме (см. [Suspense RFC](https://github.com/reactjs/rfcs/blob/main/text/0213-suspense-in-react-18.md) для получения дополнительной информации).

[См. документацию по переходам здесь](/reference/react/useTransition).

### Новые функции Suspense {/*new-suspense-features*/}

Suspense позволяет декларативно указывать состояние загрузки для части дерева компонентов, если она ещё не готова к отображению:

```js
<Suspense fallback={<Spinner />}>
  <Comments />
</Suspense>
```

Suspense делает «состояние загрузки пользовательского интерфейса» первоклассной декларативной концепцией в модели программирования React. Это позволяет нам создавать функции более высокого уровня поверх неё.

Мы представили ограниченную версию Suspense несколько лет назад. Однако единственным поддерживаемым вариантом использования было разделение кода с помощью React.lazy, и оно вообще не поддерживалось при рендеринге на сервере.

В React 18 мы добавили поддержку Suspense на сервере и расширили его возможности, используя функции конкурентного рендеринга.

Suspense в React 18 лучше всего работает в сочетании с API переходов. Если вы приостанавливаете работу во время перехода, React предотвратит замену уже видимого контента резервным. Вместо этого React отложит рендеринг до тех пор, пока не будет загружено достаточно данных, чтобы предотвратить плохое состояние загрузки.

Для получения дополнительной информации см. RFC для [Suspense в React 18](https://github.com/reactjs/rfcs/blob/main/text/0213-suspense-in-react-18.md).

### Новые API рендеринга на клиенте и сервере {/*new-client-and-server-rendering-apis*/}

В этом выпуске мы воспользовались возможностью переработать API, которые мы предоставляем для рендеринга на клиенте и сервере. Эти изменения позволяют пользователям продолжать использовать старые API в режиме React 17, пока они обновляются до новых API в React 18.

#### React DOM Client {/*react-dom-client*/}

Эти новые API теперь экспортируются из `react-dom/client`:

*   `createRoot`: новый метод для создания корня для `render` или `unmount`. Используйте его вместо `ReactDOM.render`. Новые функции в React 18 не работают без него.
*   `hydrateRoot`: новый метод для гидратации приложения, отрендеренного на сервере. Используйте его вместо `ReactDOM.hydrate` в сочетании с новыми API React DOM Server. Новые функции в React 18 не работают без него.

И `createRoot`, и `hydrateRoot` принимают новую опцию под названием `onRecoverableError` на случай, если вы хотите получать уведомления, когда React восстанавливается после ошибок во время рендеринга или гидратации для ведения журнала. По умолчанию React будет использовать [`reportError`](https://developer.mozilla.org/en-US/docs/Web/API/reportError) или `console.error` в старых браузерах.

[См. документацию по React DOM Client здесь](/reference/react-dom/client).

#### React DOM Server {/*react-dom-server*/}

Эти новые API теперь экспортируются из `react-dom/server` и имеют полную поддержку потоковой передачи Suspense на сервере:

*   `renderToPipeableStream`: для потоковой передачи в средах Node.
*   `renderToReadableStream`: для современных сред выполнения edge, таких как Deno и Cloudflare workers.

Существующий метод `renderToString` продолжает работать, но не рекомендуется.

[См. документацию по React DOM Server здесь](/reference/react-dom/server).

### Новые режимы Strict Mode {/*new-strict-mode-behaviors*/}

В будущем мы хотели бы добавить функцию, которая позволит React добавлять и удалять разделы пользовательского интерфейса, сохраняя при этом состояние. Например, когда пользователь переходит с экрана и возвращается, React должен иметь возможность сразу же показать предыдущий экран. Для этого React будет размонтировать и повторно монтировать деревья, используя то же состояние компонента, что и раньше.

Эта функция обеспечит приложениям React лучшую производительность из коробки, но требует, чтобы компоненты были устойчивы к эффектам, монтируемым и уничтожаемым несколько раз. Большинство эффектов будут работать без каких-либо изменений, но некоторые эффекты предполагают, что они монтируются или уничтожаются только один раз.

Чтобы помочь выявить эти проблемы, React 18 представляет новую проверку только для разработки в Strict Mode. Эта новая проверка будет автоматически размонтировать и повторно монтировать каждый компонент, когда компонент монтируется в первый раз, восстанавливая предыдущее состояние при втором монтировании.

До этого изменения React монтировал компонент и создавал эффекты:

```
* React монтирует компонент.
  * Создаются эффекты макета.
  * Создаются эффекты.
```

С Strict Mode в React 18 React будет имитировать размонтирование и повторное монтирование компонента в режиме разработки:

```
* React монтирует компонент.
  * Создаются эффекты макета.
  * Создаются эффекты.
* React имитирует размонтирование компонента.
  * Эффекты макета уничтожаются.
  * Эффекты уничтожаются.
* React имитирует монтирование компонента с предыдущим состоянием.
  * Создаются эффекты макета.
  * Создаются эффекты.
```

[См. документацию по обеспечению повторного использования состояния здесь](/reference/react/StrictMode#fixing-bugs-found-by-re-running-effects-in-development).

### Новые хуки {/*new-hooks*/}

#### useId {/*useid*/}

`useId` — это новый хук для генерации уникальных идентификаторов как на клиенте, так и на сервере, избегая при этом несоответствий гидратации. Он в первую очередь полезен для библиотек компонентов, интегрирующихся с API доступности, которым требуются уникальные идентификаторы. Это решает проблему, которая уже существует в React 17 и ниже, но она ещё более важна в React 18 из-за того, как новый потоковый серверный рендерер доставляет HTML вне очереди. [См. документацию здесь](/reference/react/useId).

> Примечание
>
> `useId` **не** предназначен для генерации [ключей в списке](/learn/rendering-lists#where-to-get-your-key). Ключи должны генерироваться из ваших данных.

#### useTransition {/*usetransition*/}

`useTransition` и `startTransition` позволяют пометить некоторые обновления состояния как несрочные. Другие обновления состояния по умолчанию считаются срочными. React позволит срочным обновлениям состояния (например, обновлению текстового ввода) прерывать несрочные обновления состояния (например, рендеринг списка результатов поиска). [См. документацию здесь](/reference/react/useTransition).

#### useDeferredValue {/*usedeferredvalue*/}

`useDeferredValue` позволяет отложить повторный рендеринг несрочной части дерева. Это похоже на устранение дребезга, но имеет несколько преимуществ по сравнению с ним. Нет фиксированной задержки по времени, поэтому React попытается выполнить отложенный рендеринг сразу после того, как первый рендер будет отражен на экране. Отложенный рендеринг прерываемый и не блокирует ввод пользователя. [См. документацию здесь](/reference/react/useDeferredValue).

#### useSyncExternalStore {/*usesyncexternalstore*/}

`useSyncExternalStore` — это новый хук, который позволяет внешним хранилищам поддерживать конкурентное чтение, принудительно делая обновления хранилища синхронными. Он устраняет необходимость в `useEffect` при реализации подписок на внешние источники данных и рекомендуется для любой библиотеки, которая интегрируется с состоянием, внешним по отношению к React. [См. документацию здесь](/reference/react/useSyncExternalStore).

> Примечание
>
> `useSyncExternalStore` предназначен для использования библиотеками, а не кодом приложения.

#### useInsertionEffect {/*useinsertioneffect*/}

`useInsertionEffect` — это новый хук, который позволяет CSS-in-JS библиотекам решать проблемы производительности при внедрении стилей в рендеринг. Если вы ещё не создали CSS-in-JS библиотеку, мы не ожидаем, что вы когда-либо будете использовать это. Этот хук будет выполняться после мутации DOM, но до того, как эффекты макета прочитают новый макет. Это решает проблему, которая уже существует в React 17 и ниже, но она ещё более важна в React 18, потому что React уступает браузеру во время конкурентного рендеринга, давая ему возможность пересчитать макет. [См. документацию здесь](/reference/react/useInsertionEffect).

> Примечание
>
> `useInsertionEffect` предназначен для использования библиотеками, а не кодом приложения.
