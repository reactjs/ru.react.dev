<Intro>

Как мы рассказали в [публикации о релизе](/blog/2022/03/29/react-v18), React 18 представляет новые возможности, основанные на нашем новом конкурентном рендерере, с постепенной стратегией внедрения для существующих приложений. В этой публикации мы расскажем вам, как обновиться до React 18.

Пожалуйста, [сообщайте о любых проблемах](https://github.com/facebook/react/issues/new/choose), с которыми вы столкнетесь при обновлении до React 18.

</Intro>

<Note>

Для пользователей React Native React 18 будет выпущен в будущей версии React Native. Это связано с тем, что React 18 полагается на новую архитектуру React Native, чтобы воспользоваться новыми возможностями, представленными в этой публикации блога. Для получения дополнительной информации см. [ключевой доклад React Conf здесь](https://www.youtube.com/watch?v=FZ0cG47msEk&t=1530s).

</Note>

## Установка {/*installing*/}

Чтобы установить последнюю версию React:

```bash
npm install react react-dom
```

Или, если вы используете yarn:

```bash
yarn add react react-dom
```

## Обновления API рендеринга на стороне клиента {/*updates-to-client-rendering-apis*/}

Когда вы впервые установите React 18, вы увидите предупреждение в консоли:

<ConsoleBlock level="error">

ReactDOM.render больше не поддерживается в React 18. Вместо этого используйте createRoot. Пока вы не переключитесь на новый API, ваше приложение будет вести себя так, как будто оно работает в React 17. Подробнее: https://reactjs.org/link/switch-to-createroot

</ConsoleBlock>

React 18 представляет новый root API, который обеспечивает лучшую эргономику для управления корнями. Новый root API также включает новый конкурентный рендерер, который позволяет вам использовать конкурентные возможности.

```js
// До
import { render } from 'react-dom';
const container = document.getElementById('app');
render(<App tab="home" />, container);

// После
import { createRoot } from 'react-dom/client';
const container = document.getElementById('app');
const root = createRoot(container); // createRoot(container!) if you use TypeScript
root.render(<App tab="home" />);
```

Мы также изменили `unmountComponentAtNode` на `root.unmount`:

```js
// До
unmountComponentAtNode(container);

// После
root.unmount();
```

Мы также удалили обратный вызов из render, так как он обычно не дает ожидаемого результата при использовании Suspense:

```js
// До
const container = document.getElementById('app');
render(<App tab="home" />, container, () => {
  console.log('rendered');
});

// После
function AppWithCallbackAfterRender() {
  useEffect(() => {
    console.log('rendered');
  });

  return <App tab="home" />
}

const container = document.getElementById('app');
const root = createRoot(container);
root.render(<AppWithCallbackAfterRender />);
```

<Note>

Не существует замены один к одному для старого API обратного вызова render — это зависит от вашего варианта использования. См. публикацию рабочей группы [Замена render на createRoot](https://github.com/reactwg/react-18/discussions/5) для получения дополнительной информации.

</Note>

Наконец, если ваше приложение использует рендеринг на стороне сервера с гидратацией, обновите `hydrate` до `hydrateRoot`:

```js
// До
import { hydrate } from 'react-dom';
const container = document.getElementById('app');
hydrate(<App tab="home" />, container);

// После
import { hydrateRoot } from 'react-dom/client';
const container = document.getElementById('app');
const root = hydrateRoot(container, <App tab="home" />);
// В отличие от createRoot, вам не нужен отдельный вызов root.render() здесь.
```

Для получения дополнительной информации см. [обсуждение рабочей группы здесь](https://github.com/reactwg/react-18/discussions/5).

<Note>

**Если ваше приложение не работает после обновления, проверьте, обернуто ли оно в `<StrictMode>`.** [Строгий режим стал строже в React 18](#updates-to-strict-mode), и не все ваши компоненты могут быть устойчивы к новым проверкам, которые он добавляет в режиме разработки. Если удаление Strict Mode исправит ваше приложение, вы можете удалить его во время обновления, а затем добавить его обратно (либо вверху, либо для части дерева) после того, как вы исправите проблемы, на которые он указывает.

</Note>

## Обновления API рендеринга на стороне сервера {/*updates-to-server-rendering-apis*/}

В этом выпуске мы перерабатываем наши API `react-dom/server`, чтобы полностью поддерживать Suspense на сервере и потоковую передачу SSR. В рамках этих изменений мы **устареваем** старый API потоковой передачи Node, который не поддерживает инкрементную потоковую передачу Suspense на сервере.

Использование этого API теперь будет предупреждать:

* `renderToNodeStream`: **Устаревший ⛔️️**

Вместо этого для потоковой передачи в средах Node используйте:
* `renderToPipeableStream`: **Новый ✨**

Мы также представляем новый API для поддержки потоковой передачи SSR с Suspense для современных сред выполнения edge, таких как Deno и Cloudflare workers:
* `renderToReadableStream`: **Новый ✨**

Следующие API будут продолжать работать, но с ограниченной поддержкой Suspense:
* `renderToString`: **Ограничено** ⚠️
* `renderToStaticMarkup`: **Ограничено** ⚠️

Наконец, этот API будет продолжать работать для рендеринга электронных писем:
* `renderToStaticNodeStream`

Для получения дополнительной информации об изменениях в API рендеринга на стороне сервера см. публикацию рабочей группы [Обновление до React 18 на сервере](https://github.com/reactwg/react-18/discussions/22), [подробный обзор новой архитектуры Suspense SSR](https://github.com/reactwg/react-18/discussions/37) и выступление [Shaundai Person](https://twitter.com/shaundai) о [Потоковой передаче рендеринга на стороне сервера с Suspense](https://www.youtube.com/watch?v=pj5N-Khihgc) на React Conf 2021.

## Обновления определений TypeScript {/*updates-to-typescript-definitions*/}

Если ваш проект использует TypeScript, вам потребуется обновить ваши зависимости `@types/react` и `@types/react-dom` до последних версий. Новые типы более безопасны и выявляют проблемы, которые раньше игнорировались проверкой типов. Наиболее заметным изменением является то, что проп `children` теперь необходимо указывать явно при определении пропсов, например:

```typescript{3}
interface MyButtonProps {
  color: string;
  children?: React.ReactNode;
}
```

См. [запрос на включение типизации React 18](https://github.com/DefinitelyTyped/DefinitelyTyped/pull/56210) для получения полного списка изменений, касающихся только типов. Он содержит ссылки на исправления примеров в типах библиотек, чтобы вы могли увидеть, как настроить свой код. Вы можете использовать [автоматизированный скрипт миграции](https://github.com/eps1lon/types-react-codemod), чтобы быстрее перенести код вашего приложения на новые и более безопасные типы.

Если вы обнаружите ошибку в типизации, пожалуйста, [создайте ишью](https://github.com/DefinitelyTyped/DefinitelyTyped/discussions/new?category=issues-with-a-types-package) в репозитории DefinitelyTyped.

## Автоматическая группировка {/*automatic-batching*/}

React 18 добавляет улучшения производительности из коробки, выполняя больше группировки по умолчанию. Группировка — это когда React группирует несколько обновлений состояния в один повторный рендер для повышения производительности. До React 18 мы группировали обновления только внутри обработчиков событий React. Обновления внутри промисов, setTimeout, нативных обработчиков событий или любых других событий по умолчанию не группировались в React:

```js
// До React 18 только события React группировались

function handleClick() {
  setCount(c => c + 1);
  setFlag(f => !f);
  // React перерендерит только один раз в конце (это группировка!)
}

setTimeout(() => {
  setCount(c => c + 1);
  setFlag(f => !f);
  // React перерендерит дважды, по одному разу для каждого обновления состояния (без группировки)
}, 1000);
```

Начиная с React 18 с `createRoot`, все обновления будут автоматически группироваться, независимо от того, откуда они исходят. Это означает, что обновления внутри таймаутов, промисов, нативных обработчиков событий или любых других событий будут группироваться так же, как и обновления внутри событий React:

```js
// После React 18 обновления внутри таймаутов, промисов,
// нативных обработчиков событий или любых других событий группируются.

function handleClick() {
  setCount(c => c + 1);
  setFlag(f => !f);
  // React перерендерит только один раз в конце (это группировка!)
}

setTimeout(() => {
  setCount(c => c + 1);
  setFlag(f => !f);
  // React перерендерит только один раз в конце (это группировка!)
}, 1000);
```

Это критическое изменение, но мы ожидаем, что это приведет к меньшему объему работы по рендерингу и, следовательно, к повышению производительности в ваших приложениях. Чтобы отказаться от автоматической группировки, вы можете использовать `flushSync`:

```js
import { flushSync } from 'react-dom';

function handleClick() {
  flushSync(() => {
    setCounter(c => c + 1);
  });
  // React обновил DOM к настоящему моменту
  flushSync(() => {
    setFlag(f => !f);
  });
  // React обновил DOM к настоящему моменту
}
```

Для получения дополнительной информации см. [Подробный обзор автоматической группировки](https://github.com/reactwg/react-18/discussions/21).

## Новые API для библиотек {/*new-apis-for-libraries*/}

В рабочей группе React 18 мы работали с сопровождающими библиотек, чтобы создать новые API, необходимые для поддержки конкурентного рендеринга для вариантов использования, специфичных для их варианта использования, в таких областях, как стили и внешние хранилища. Чтобы поддержать React 18, некоторым библиотекам может потребоваться переключиться на один из следующих API:

* `useSyncExternalStore` — это новый хук, который позволяет внешним хранилищам поддерживать конкурентное чтение, принудительно делая обновления хранилища синхронными. Этот новый API рекомендуется для любой библиотеки, которая интегрируется с состоянием, внешним по отношению к React. Для получения дополнительной информации см. [обзорную публикацию useSyncExternalStore](https://github.com/reactwg/react-18/discussions/70) и [подробности API useSyncExternalStore](https://github.com/reactwg/react-18/discussions/86).
* `useInsertionEffect` — это новый хук, который позволяет CSS-in-JS библиотекам решать проблемы производительности при внедрении стилей в рендеринг. Если вы еще не создали библиотеку CSS-in-JS, мы не ожидаем, что вы когда-либо будете использовать это. Этот хук будет выполняться после мутации DOM, но до того, как эффекты макета прочитают новый макет. Это решает проблему, которая уже существует в React 17 и ниже, но еще более важна в React 18, потому что React уступает браузеру во время конкурентного рендеринга, давая ему возможность пересчитать макет. Для получения дополнительной информации см. [Руководство по обновлению библиотеки для `<style>`](https://github.com/reactwg/react-18/discussions/110).

React 18 также представляет новые API для конкурентного рендеринга, такие как `startTransition`, `useDeferredValue` и `useId`, о которых мы подробнее рассказываем в [публикации о релизе](/blog/2022/03/29/react-v18).

## Обновления строгого режима {/*updates-to-strict-mode*/}

В будущем мы хотели бы добавить функцию, которая позволит React добавлять и удалять разделы пользовательского интерфейса, сохраняя при этом состояние. Например, когда пользователь переходит с экрана и возвращается, React должен иметь возможность сразу же показать предыдущий экран. Для этого React будет размонтировать и повторно монтировать деревья, используя то же состояние компонента, что и раньше.

Эта функция обеспечит React лучшую производительность из коробки, но требует, чтобы компоненты были устойчивы к эффектам, монтируемым и уничтожаемым несколько раз. Большинство эффектов будут работать без каких-либо изменений, но некоторые эффекты предполагают, что они монтируются или уничтожаются только один раз.

Чтобы помочь выявить эти проблемы, React 18 представляет новую проверку только для разработки в Strict Mode. Эта новая проверка будет автоматически размонтировать и повторно монтировать каждый компонент, когда компонент монтируется в первый раз, восстанавливая предыдущее состояние при втором монтировании.

До этого изменения React монтировал компонент и создавал эффекты:

```
* React монтирует компонент.
    * Создаются эффекты макета.
    * Создаются эффекты эффектов.
```

Со Strict Mode в React 18 React будет имитировать размонтирование и повторное монтирование компонента в режиме разработки:

```
* React монтирует компонент.
    * Создаются эффекты макета.
    * Создаются эффекты эффектов.
* React имитирует размонтирование компонента.
    * Эффекты макета уничтожаются.
    * Эффекты уничтожаются.
* React имитирует монтирование компонента с предыдущим состоянием.
    * Запускается код настройки эффекта макета
    * Запускается код настройки эффекта
```

Для получения дополнительной информации см. публикации рабочей группы [Добавление повторно используемого состояния в StrictMode](https://github.com/reactwg/react-18/discussions/19) и [Как поддерживать повторно используемое состояние в эффектах](https://github.com/reactwg/react-18/discussions/18).

## Настройка среды тестирования {/*configuring-your-testing-environment*/}

Когда вы впервые обновите свои тесты для использования `createRoot`, вы можете увидеть это предупреждение в консоли тестов:

<ConsoleBlock level="error">

Текущая среда тестирования не настроена для поддержки act(...)

</ConsoleBlock>

Чтобы исправить это, установите `globalThis.IS_REACT_ACT_ENVIRONMENT` в `true` перед запуском теста:

```js
// В вашем файле настройки теста
globalThis.IS_REACT_ACT_ENVIRONMENT = true;
```

Цель этого флага — сообщить React, что он работает в среде, похожей на модульный тест. React будет регистрировать полезные предупреждения, если вы забудете обернуть обновление с помощью `act`.

Вы также можете установить флаг в `false`, чтобы сообщить React, что `act` не требуется. Это может быть полезно для сквозных тестов, которые имитируют полную среду браузера.

В конечном итоге мы ожидаем, что библиотеки тестирования настроят это для вас автоматически. Например, [следующая версия React Testing Library имеет встроенную поддержку React 18](https://github.com/testing-library/react-testing-library/issues/509#issuecomment-917989936) без какой-либо дополнительной настройки.

[Более подробная информация об API тестирования `act` и связанных изменениях](https://github.com/reactwg/react-18/discussions/102) доступна в рабочей группе.

## Отказ от поддержки Internet Explorer {/*dropping-support-for-internet-explorer*/}

В этом выпуске React отказывается от поддержки Internet Explorer, [поддержка которого прекращается 15 июня 2022 г.](https://blogs.windows.com/windowsexperience/2021/05/19/the-future-of-internet-explorer-on-windows-10-is-in-microsoft-edge). Мы вносим это изменение сейчас, потому что новые функции, представленные в React 18, созданы с использованием современных функций браузера, таких как микрозадачи, которые невозможно адекватно полифилить в IE.

Если вам нужно поддерживать Internet Explorer, мы рекомендуем вам остаться с React 17.

## Другие критические изменения {/*other-breaking-changes*/}

* **Согласованность времени выполнения `useEffect`**: React теперь всегда синхронно сбрасывает функции эффектов, если обновление было вызвано во время дискретного события пользовательского ввода, такого как клик или событие keydown. Ранее поведение не всегда было предсказуемым или согласованным.
* **Более строгие ошибки гидратации**: Несоответствия гидратации из-за отсутствующего или лишнего текстового контента теперь рассматриваются как ошибки, а не как предупреждения. React больше не будет пытаться «исправить» отдельные узлы, вставляя или удаляя узел на клиенте в попытке сопоставить разметку сервера, и вернётся к клиентскому рендерингу до ближайшей границы `<Suspense>` в дереве. Это гарантирует, что гидратированное дерево будет согласованным и позволит избежать потенциальных дыр в конфиденциальности и безопасности, которые могут быть вызваны несоответствиями гидратации.
* **Деревья Suspense всегда согласованы:** Если компонент приостанавливается до того, как он будет полностью добавлен в дерево, React не будет добавлять его в дерево в неполном состоянии или запускать его эффекты. Вместо этого React полностью отбросит новое дерево, дождётся завершения асинхронной операции, а затем повторит рендеринг с нуля. React будет выполнять попытку повторного рендеринга одновременно и без блокировки браузера.
* **Эффекты макета с Suspense**: Когда дерево повторно приостанавливается и возвращается к резервному варианту, React теперь очистит эффекты макета, а затем повторно создаст их, когда содержимое внутри границы снова будет показано. Это исправляет проблему, которая не позволяла библиотекам компонентов правильно измерять макет при использовании с Suspense.
* **Новые требования к среде JavaScript**: React теперь зависит от современных функций браузеров, включая `Promise`, `Symbol` и `Object.assign`. Если вы поддерживаете более старые браузеры и устройства, такие как Internet Explorer, которые не предоставляют современные функции браузера изначально или имеют несовместимые реализации, рассмотрите возможность включения глобального полифилла в ваше скомпилированное приложение.

## Другие заметные изменения {/*other-notable-changes*/}

### React {/*react*/}

* **Компоненты теперь могут рендерить `undefined`**: React больше не выдаёт предупреждение, если вы возвращаете `undefined` из компонента. Это делает допустимые значения, возвращаемые компонентом, согласованными со значениями, которые разрешены в середине дерева компонентов. Мы предлагаем использовать линтер, чтобы избежать ошибок, таких как забывание оператора `return` перед JSX.
* **В тестах предупреждения `act` теперь являются опциональными**: Если вы запускаете сквозные тесты, предупреждения `act` излишни. Мы внедрили [механизм](https://github.com/reactwg/react-18/discussions/102) с возможностью выбора, чтобы вы могли включать их только для модульных тестов, где они полезны и выгодны.
* **Отсутствие предупреждения о `setState` в несмонтированных компонентах**: Ранее React предупреждал об утечках памяти, когда вы вызывали `setState` в несмонтированном компоненте. Это предупреждение было добавлено для подписок, но люди в основном сталкиваются с ним в сценариях, где установка состояния в порядке вещей, а обходные пути ухудшают код. Мы [удалили](https://github.com/facebook/react/pull/22114) это предупреждение.
* **Отсутствие подавления журналов консоли**: Когда вы используете Strict Mode, React дважды рендерит каждый компонент, чтобы помочь вам найти непредвиденные побочные эффекты. В React 17 мы подавляли журналы консоли для одного из двух рендеров, чтобы журналы было легче читать. В ответ на [отзывы сообщества](https://github.com/facebook/react/issues/21783) о том, что это сбивает с толку, мы удалили подавление. Вместо этого, если у вас установлены React DevTools, рендеры второго журнала будут отображаться серым цветом, и будет опция (отключена по умолчанию) для их полного подавления.
* **Улучшено использование памяти**: React теперь очищает больше внутренних полей при размонтировании, что делает влияние неисправленных утечек памяти, которые могут существовать в коде вашего приложения, менее серьёзным.

### React DOM Server {/*react-dom-server*/}

* **`renderToString`**: Больше не будет выдавать ошибку при приостановке на сервере. Вместо этого он будет выдавать резервный HTML для ближайшей границы `<Suspense>`, а затем повторно попытается отобразить то же содержимое на клиенте. По-прежнему рекомендуется переключиться на потоковый API, такой как `renderToPipeableStream` или `renderToReadableStream`.
* **`renderToStaticMarkup`**: Больше не будет выдавать ошибку при приостановке на сервере. Вместо этого он будет выдавать резервный HTML для ближайшей границы `<Suspense>`.
