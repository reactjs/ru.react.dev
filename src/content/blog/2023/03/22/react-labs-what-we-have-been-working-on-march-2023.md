## React Server Components {/*react-server-components*/}

React Server Components (или RSC) — это новая архитектура приложений, разработанная командой React.

Мы впервые поделились нашими исследованиями RSC во [вводном докладе](/blog/2020/12/21/data-fetching-with-react-server-components) и [RFC](https://github.com/reactjs/rfcs/pull/188). Чтобы кратко напомнить, мы представляем новый тип компонентов — Server Components — которые выполняются заранее и исключаются из вашего JavaScript-бандла. Server Components могут выполняться во время сборки, позволяя вам читать из файловой системы или получать статический контент. Они также могут выполняться на сервере, позволяя вам получить доступ к вашему слою данных без необходимости создавать API. Вы можете передавать данные через пропсы из Server Components в интерактивные Client Components в браузере.

RSC объединяет простую модель мышления «запрос/ответ» многостраничных приложений (Multi-Page Apps), ориентированных на сервер, с бесшовной интерактивностью одностраничных приложений (Single-Page Apps), ориентированных на клиент, предоставляя вам лучшее из обоих миров.

С момента нашего последнего обновления мы объединили [React Server Components RFC](https://github.com/reactjs/rfcs/blob/main/text/0188-server-components.md) для ратификации предложения. Мы решили нерешенные вопросы с предложением [React Server Module Conventions](https://github.com/reactjs/rfcs/blob/main/text/0227-server-module-conventions.md) и достигли консенсуса с нашими партнерами относительно соглашения `"use client"`. Эти документы также служат спецификацией того, что должна поддерживать реализация, совместимая с RSC.

Самым большим изменением является то, что мы ввели [`async` / `await`](https://github.com/reactjs/rfcs/pull/229) как основной способ получения данных из Server Components. Мы также планируем поддерживать загрузку данных с клиента, вводя новый хук под названием `use`, который разворачивает промисы. Хотя мы не можем поддерживать `async / await` в произвольных компонентах в приложениях, состоящих только из клиента, мы планируем добавить поддержку, когда вы структурируете свое приложение, состоящее только из клиента, аналогично тому, как структурированы приложения RSC.

Теперь, когда получение данных в значительной степени решено, мы исследуем другое направление: передачу данных с клиента на сервер, чтобы вы могли выполнять мутации базы данных и реализовывать формы. Мы делаем это, позволяя передавать функции Server Actions через границу сервера/клиента, которые клиент затем может вызывать, обеспечивая бесшовный RPC. Server Actions также предоставляют вам формы с прогрессивным улучшением до загрузки JavaScript.

React Server Components были выпущены в [Next.js App Router](/learn/start-a-new-react-project#nextjs-app-router). Это демонстрирует глубокую интеграцию маршрутизатора, который действительно использует RSC как примитив, но это не единственный способ построить совместимый с RSC маршрутизатор и фреймворк. Существует четкое разделение функций, предоставляемых спецификацией RSC, и их реализацией. React Server Components предназначены как спецификация для компонентов, которые работают в совместимых фреймворках React.

Мы обычно рекомендуем использовать существующий фреймворк, но если вам нужно создать свой собственный пользовательский фреймворк, это возможно. Создание собственного фреймворка, совместимого с RSC, не так просто, как нам хотелось бы, в основном из-за глубокой интеграции бандлера, которая необходима. Текущее поколение бандлеров отлично подходит для использования на клиенте, но они не были разработаны с первоклассной поддержкой разделения единого графа модулей между сервером и клиентом. Вот почему мы теперь напрямую сотрудничаем с разработчиками бандлеров, чтобы получить примитивы для RSC, встроенные в них.

## Загрузка ресурсов {/*asset-loading*/}

[Suspense](/reference/react/Suspense) позволяет указать, что отображать на экране во время загрузки данных или кода для ваших компонентов. Это позволяет вашим пользователям постепенно видеть больше контента во время загрузки страницы, а также во время навигации по маршрутам, которые загружают больше данных и кода. Однако с точки зрения пользователя загрузка данных и рендеринг не рассказывают всей истории, когда речь идет о готовности нового контента. По умолчанию браузеры загружают таблицы стилей, шрифты и изображения независимо, что может привести к скачкам пользовательского интерфейса и последовательным сдвигам макета.

Мы работаем над полной интеграцией Suspense с жизненным циклом загрузки таблиц стилей, шрифтов и изображений, чтобы React учитывал их при определении готовности контента к отображению. Без каких-либо изменений в том, как вы пишете свои компоненты React, обновления будут вести себя более согласованно и приятно. В качестве оптимизации мы также предоставим ручной способ предварительной загрузки ресурсов, таких как шрифты, непосредственно из компонентов.

В настоящее время мы внедряем эти функции и скоро поделимся дополнительной информацией.

## Метаданные документа {/*document-metadata*/}

Различные страницы и экраны в вашем приложении могут иметь разные метаданные, такие как тег `<title>`, описание и другие теги `<meta>`, специфичные для этого экрана. С точки зрения обслуживания, более масштабно хранить эту информацию рядом с компонентом React для этой страницы или экрана. Однако HTML-теги для этих метаданных должны находиться в `<head>` документа, который обычно рендерится в компоненте в самом корне вашего приложения.

Сегодня люди решают эту проблему одним из двух способов.

Один из способов — рендерить специальный сторонний компонент, который перемещает `<title>`, `<meta>` и другие теги внутри него в `<head>` документа. Это работает для основных браузеров, но существует множество клиентов, которые не запускают JavaScript на стороне клиента, например парсеры Open Graph, поэтому этот метод не является универсально подходящим.

Другой способ — серверный рендеринг страницы в двух частях. Сначала рендерится основной контент и собираются все такие теги. Затем рендерится `<head>` с этими тегами. Наконец, `<head>` и основной контент отправляются в браузер. Этот подход работает, но он мешает вам воспользоваться преимуществами [Streaming Server Renderer React 18](/reference/react-dom/server/renderToReadableStream), поскольку вам придется ждать рендеринга всего контента, прежде чем отправлять `<head>`.

Вот почему мы добавляем встроенную поддержку рендеринга тегов `<title>`, `<meta>` и метаданных `<link>` в любом месте вашего дерева компонентов из коробки. Это будет работать одинаково во всех средах, включая полностью клиентский код, SSR и, в будущем, RSC. Мы скоро поделимся более подробной информацией об этом.

## React Optimizing Compiler {/*react-optimizing-compiler*/}

С момента нашего предыдущего обновления мы активно работали над дизайном [React Forget](/blog/2022/06/15/react-labs-what-we-have-been-working-on-june-2022#react-compiler), оптимизирующего компилятора для React. Ранее мы говорили о нем как о «компиляторе с автоматическим мемоизированием», и в некотором смысле это правда. Но создание компилятора помогло нам еще глубже понять модель программирования React. Лучший способ понять React Forget — это рассматривать его как автоматический компилятор *реактивности*.

Основная идея React заключается в том, что разработчики определяют свой пользовательский интерфейс как функцию текущего состояния. Вы работаете с обычными значениями JavaScript — числами, строками, массивами, объектами — и используете стандартные идиомы JavaScript — if/else, for и т. д. — для описания логики вашего компонента. Ментальная модель заключается в том, что React будет повторно рендерить всякий раз, когда изменяется состояние приложения. Мы считаем, что эта простая ментальная модель и близость к семантике JavaScript являются важными принципами модели программирования React.

Проблема в том, что React иногда может быть *слишком* реактивным: он может рендерить слишком много. Например, в JavaScript у нас нет дешевых способов сравнить, эквивалентны ли два объекта или массива (имеют ли они одинаковые ключи и значения), поэтому создание нового объекта или массива при каждом рендеринге может привести к тому, что React будет выполнять больше работы, чем строго необходимо. Это означает, что разработчики должны явно мемоизировать компоненты, чтобы не чрезмерно реагировать на изменения.

Наша цель с React Forget — обеспечить, чтобы приложения React имели ровно столько реактивности, сколько нужно по умолчанию: чтобы приложения повторно рендерились только тогда, когда значения состояния *значимо* изменяются. С точки зрения реализации это означает автоматическое мемоизирование, но мы считаем, что концепция реактивности — лучший способ понять React и Forget. Один из способов взглянуть на это — то, что React в настоящее время повторно рендерит при изменении идентичности объекта. С Forget React повторно рендерит при изменении семантического значения — но без накладных расходов на глубокие сравнения во время выполнения.

С точки зрения конкретного прогресса, с момента нашего последнего обновления мы существенно доработали дизайн компилятора, чтобы соответствовать этому подходу автоматической реактивности и учесть отзывы об использовании компилятора внутри компании. После некоторых значительных рефакторингов компилятора, начавшихся в конце прошлого года, мы начали использовать компилятор в продакшене в ограниченных областях в Meta. Мы планируем сделать его открытым исходным кодом, как только докажем его эффективность в продакшене.

Наконец, многие люди выразили интерес к тому, как работает компилятор. Мы с нетерпением ждем возможности поделиться гораздо большим количеством деталей, когда мы докажем эффективность компилятора и сделаем его открытым исходным кодом. Но сейчас мы можем поделиться несколькими моментами:

Ядро компилятора почти полностью отделено от Babel, а основной API компилятора (грубо говоря) принимает старый AST и выдает новый AST (сохраняя при этом данные о расположении исходного кода). Под капотом мы используем собственное представление кода и конвейер преобразований для выполнения низкоуровневого семантического анализа. Однако основной публичный интерфейс к компилятору будет осуществляться через Babel и другие плагины системы сборки. Для простоты тестирования у нас в настоящее время есть плагин Babel, который представляет собой очень тонкую обертку, вызывающую компилятор для генерации новой версии каждой функции и ее замены.

Поскольку мы рефакторили компилятор в течение последних нескольких месяцев, мы хотели сосредоточиться на уточнении основной модели компиляции, чтобы гарантировать, что мы сможем обрабатывать такие сложности, как условные операторы, циклы, переприсваивание и мутации. Однако в JavaScript есть много способов выразить каждую из этих функций: if/else, тернарные операторы, for, for-in, for-of и т. д. Попытка поддержать полный язык заранее задержала бы момент, когда мы могли бы проверить основную модель. Вместо этого мы начали с небольшого, но репрезентативного подмножества языка: let/const, if/else, циклы for, объекты, массивы, примитивы, вызовы функций и несколько других функций. По мере того, как мы набирались уверенности в основной модели и уточняли наши внутренние абстракции, мы расширяли поддерживаемое подмножество языка. Мы также явно указываем на синтаксис, который мы еще не поддерживаем, регистрируя диагностические сообщения и пропуская компиляцию для неподдерживаемого ввода. У нас есть утилиты для тестирования компилятора на кодовых базах Meta и проверки того, какие неподдерживаемые функции наиболее распространены, чтобы мы могли расставить приоритеты для них в первую очередь. Мы будем продолжать постепенно расширяться, чтобы поддерживать весь язык.

Чтобы сделать обычный JavaScript в компонентах React реактивным, требуется компилятор с глубоким пониманием семантики, чтобы он мог точно понимать, что делает код. Применяя этот подход, мы создаем систему реактивности в JavaScript, которая позволяет вам писать продуктовый код любой сложности с полной выразительностью языка, вместо того чтобы ограничиваться предметно-ориентированным языком.

## Offscreen Rendering {/*offscreen-rendering*/}

Offscreen rendering — это предстоящая возможность React для рендеринга экранов в фоновом режиме без дополнительных накладных расходов на производительность. Вы можете рассматривать это как версию [CSS-свойства `content-visibility`](https://developer.mozilla.org/en-US/docs/Web/CSS/content-visibility), которая работает не только для DOM-элементов, но и для компонентов React. В ходе наших исследований мы обнаружили различные варианты использования:

- Маршрутизатор может предварительно рендерить экраны в фоновом режиме, чтобы при переходе пользователя к ним они были мгновенно доступны.
- Компонент переключения вкладок может сохранять состояние скрытых вкладок, чтобы пользователь мог переключаться между ними, не теряя своего прогресса.
- Компонент виртуализированного списка может предварительно рендерить дополнительные строки выше и ниже видимого окна.
- При открытии модального окна или всплывающего окна остальная часть приложения может быть переведена в «фоновый» режим, чтобы события и обновления были отключены для всего, кроме модального окна.

Большинство разработчиков React не будут напрямую взаимодействовать с API React для offscreen rendering. Вместо этого offscreen rendering будет интегрирован в такие вещи, как маршрутизаторы и библиотеки пользовательского интерфейса, а затем разработчики, использующие эти библиотеки, автоматически получат преимущества без дополнительных усилий.

Идея заключается в том, что вы должны иметь возможность рендерить любое дерево React вне экрана, не изменяя способ написания ваших компонентов. Когда компонент рендерится вне экрана, он на самом деле не *монтируется*, пока компонент не станет видимым — его эффекты не срабатывают. Например, если компонент использует `useEffect` для логирования аналитики при первом появлении, предварительный рендеринг не повлияет на точность этой аналитики. Аналогично, когда компонент уходит за пределы экрана, его эффекты также размонтируются. Ключевой особенностью offscreen rendering является то, что вы можете переключать видимость компонента, не теряя его состояние.

С момента нашего последнего обновления мы протестировали экспериментальную версию предварительного рендеринга внутри Meta в наших приложениях React Native на Android и iOS с положительными результатами производительности. Мы также улучшили работу offscreen rendering с Suspense — приостановка внутри дерева вне экрана не будет вызывать резервные варианты Suspense. Наша оставшаяся работа включает в себя финализацию примитивов, которые предоставляются разработчикам библиотек. Мы ожидаем опубликовать RFC позднее в этом году, наряду с экспериментальным API для тестирования и обратной связи.

## Transition Tracing {/*transition-tracing*/}

API Transition Tracing позволяет обнаруживать, когда [React Transitions](/reference/react/useTransition) становятся медленнее, и исследовать причины их медленной работы. После нашего последнего обновления мы завершили первоначальный дизайн API и опубликовали [RFC](https://github.com/reactjs/rfcs/pull/238). Основные возможности также были реализованы. В настоящее время проект приостановлен. Мы приветствуем отзывы о RFC и надеемся возобновить его разработку, чтобы предоставить лучший инструмент для измерения производительности React. Это будет особенно полезно для маршрутизаторов, построенных поверх React Transitions, таких как [Next.js App Router](/learn/start-a-new-react-project#nextjs-app-router).
